# Desktop calendar storage

Existing `calendar/workspace.sqlite3` databases always take priority. Setup validates them without migrating, replacing or silently creating over invalid bytes.

For a new store, trusted setup runs on the isolated operation thread, with its own bounded setup budget. The ordinary five-second calendar processing limit is unchanged. Schema DDL uses one transaction. A private sibling `workspace-v1.stage-<UUID>` directory receives the database; setup closes SQLite, checks integrity and application/schema identity, rejects sidecars, then writes, flushes and closes a bounded `ready.pending` manifest sealing the initial bytes before renaming it to `ready.json`. A same-directory directory rename publishes the closed database and manifest together as `workspace-v1`. A nonempty concurrent winner is verified and used, never overwritten. If a peer publishes the sealed stage before its creator finishes verification, the creator adopts that verified winner only after proving its private stage disappeared. Explicit initialization and flush errors remain visible.

The manifest hash seals initial publication only. Later ordinary calendar edits change SQLite bytes; reopening verifies the supported database rather than comparing saved work against the initial empty hash.

Existing saved databases normally receive read-only validation. The precise SQLite `SQLITE_READONLY_ROLLBACK` condition is handled only after verifying the Vantage SQLite header and a regular bounded rollback journal: SQLite performs its normal recovery, closes, and the database is verified read-only again. No interrupted mutation is replayed, and foreign or unsupported headers are retained without repair.

A complete sealed private stage can finish publication after an interruption. Incomplete, changed, ambiguous or unclosed private data is retained with a visible setup error. Existing invalid legacy/published data is also retained. Setup never truncates a destination or falls back to copying a database into a visible final filename. A concurrent setup can wait for the winner within a finite budget.

The directory publish avoids exFAT's unsupported hardlinks and the partial-destination window of an exclusive file-copy fallback. Regular database and manifest flush failures retain private setup. Unsupported/refused directory or volume flushes are best effort; an unexpected post-publication directory flush error is reported while the published generation is retained for verification on refresh. This is a process-interruption contract; it does not promise universal power-loss durability on exFAT, removable media, network filesystems or storage hardware. Recovery validates the database and manifest before use and leaves unverifiable state untouched.
